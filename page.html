      The Fossil Delta Format

      Fossil stores many versions of a file as a delta: a short recipe that rebuilds one byte sequence from another it resembles. Here is a real one, from the draft's own worked example. These 79 bytes rebuild a 151-byte file.

      The delta, byte by byte. Point at a segment to read it.source 102 B · delta 79 B · target 151 B
      Header, four segments, and a trailer. Nothing else.
      header and trailer copy from the source literal bytes carried in the delta

      §1–2What a delta is

      Over a project's life, most versions of a file differ from the previous one by a few lines. Storing every version whole would waste space, so Fossil stores many of them as deltas. A delta encodes one byte sequence, the target, as instructions for rebuilding it from another, the source.

      There are two instructions: copy a run of bytes from the source, and insert a run of bytes carried in the delta itself. Where the target shares long runs with the source, the copies make the delta much smaller than the target.

      A delta does not name its source. The caller supplies the source, and the storage or transfer layer records which source a delta belongs to. Naming stored content and verifying its integrity belongs to the Fossil Artifact Format. This document covers only the delta's bytes and how to apply them.

      TermMeaning
      SourceThe bytes a delta is applied against.
      TargetThe bytes a delta rebuilds. The delta's header declares its length.
      DeltaThe bytes that say how to rebuild the target from the source.
      SegmentOne instruction in a delta: a copy or a literal.

      The draft uses MUST, SHOULD and MAY in the BCP 14 sense, and only when capitalised.

      §3The shape of a delta

      A delta is a header, zero or more segments, and a trailer, written back to back with no separators beyond the bytes each part defines. Every number in it uses the same base-64 integer encoding.

      header    integer LF                 target length, then 0x0a
copy      count "@" offset ","       copy count source bytes from offset
literal   count ":" payload          insert the next count bytes of the delta
trailer   checksum ";"               32-bit sum of the target

      The opcode that follows an integer says what the integer was: @ starts a copy, : a literal, ; the trailer. A reader never needs to look ahead further than one byte.

      §3.1Integers in base 64

      An integer is an unsigned number written in base 64, most significant digit first, with no leading zeros. Zero is the single character 0. The 64 digits, in value order:

      So 0–9 are 0–9, A–Z are 10–35, _ is 36, a–z are 37–62 and ~ is 63. A reader takes digits until the first byte that is not one; that byte is the opcode or separator. Bytes 0x80–0xFF are never digits and always end an integer.

      Convert an integerType a decimal number or a base-64 string

      Producers MUST use the canonical form, and every value they emit MUST be below 232. Decoders are allowed more slack. Fossil as shipped accepts an empty integer (read as zero) and leading zeros (read as their value). A decoder MAY reject either form, and implementations differ. Values at or above 232 have no interoperable meaning: a decoder MAY reject them, and one that accumulates in 32 bits will wrap where a wider one will not.

      §3.2The header

      The header is the target length as an integer, followed by the byte 0x0a. The decoder reads it first, so it knows how large the output will be before it reads any segment. A decoder MUST reject a delta whose header integer is not immediately followed by 0x0a. In the example, 2N is 2 × 64 + 23 = 151.

      §3.3Copy and literal segments

      Copy is count@offset,. It copies count bytes from the source, starting at the zero-based offset, onto the end of the output. The comma is required. A count of zero copies zero bytes, and encoders MUST NOT emit one. Whether the run lies inside the source is checked when the delta is applied.

      Literal is count:payload. The next count bytes of the delta go straight to the output. The payload is opaque and may contain any byte, including 0x0a. A reader MUST count exactly count bytes past the colon and MUST NOT scan for a separator. The only structural 0x0a in a delta is the one that ends the header.

      §3.4The trailer and its checksum

      The delta ends with checksum;. Producers MUST always write the checksum. Decoders MAY verify it, and a decoder that verifies MUST reject a mismatch. A decoder that does not verify still requires the trailer's syntax.

      The checksum reads the target as big-endian 32-bit words and adds them, wrapping at 232. A tail of one to three bytes is added as if padded with zeros to a whole word: the first tail byte shifted left 24 bits, the second 16, the third 8.

      For the 151-byte example target, the 37 whole words sum to 0x2CE563A1. The tail 6C 2E 0A adds 0x6C2E0A00, giving 0x99136DA1, which is 2568187297 or 2P4rrX in base 64: the trailer.

      Checksum any textUTF-8 bytes, as the trailer would carry them

      After the trailer the delta is complete. Bytes that follow it in the buffer MAY be ignored.

      §4Applying a delta

      The reader is given the source bytes and the delta bytes and works through the delta once, front to back:

      1. Reject a delta that is zero bytes long.
      2. Read the header integer as the target length. Reject unless the next byte is 0x0a. Allocate the output and set the position to zero.
      3. While delta bytes remain, read an integer and look at the byte after it.
        • @: read the offset and require a comma. Reject if offset + count exceeds the source, computed without overflow. Reject if the copy would run past the target length. Otherwise copy and advance.
        • :: reject if count exceeds the bytes left in the delta, or if the literal would run past the target length. Otherwise copy the payload and advance past it.
        • ;: reject unless the position equals the target length. If the decoder verifies, check the checksum. The output is the target.
        • Any other byte: reject.
      4. Reject a delta that ends without ;.

      §4When a decoder must refuse

      A decoder MUST report failure for every condition below, beyond the zero-length delta of step 1. Whether it reports one code or one per condition is up to the implementation. Each Try it loads a delta that breaks that rule into the playground below.

      #Condition

      Empty integers, leading zeros and values at or above 232 are not on this list. A decoder that accepts them still applies every structural and bounds check to the value it uses. A decoder MUST NOT require or reject a particular segmentation, hash window, chain depth or copy strategy: those are encoder choices, not part of the format.

      ∗Playground

      Edit the source and target to see the delta Fossil's encoder would write and the decoder applying it. You can also edit the delta directly. Write a line feed as \n and any other byte as \xNN.

      §4.1Asking only for the size

      A reader MAY learn the target length by reading just the header integer and its 0x0a, without looking at anything after it. It MUST fail on an empty buffer or a header not followed by 0x0a, and needs no further bytes to succeed. Fossil uses this to allocate the output before applying a delta.

      §4.2When the source is missing

      The decoder works on bytes already in memory. It cannot ask for a missing source or wait for one, so the caller MUST supply the whole source first and SHOULD check it is available. When a repository receives a delta whose source it does not hold, it records the dependency and rebuilds the target later, once the source arrives from a peer through the Fossil Sync Protocol.

      §5How Fossil's encoder finds copies

      Informative. The format allows any segmentation that rebuilds the target exactly.

      Any sequence of copies and literals that reproduces the target is a valid delta. The draft leaves the search to the encoder. Fossil's own encoder, which the playground runs, works like this:

      1. Cut the source into 16-byte blocks and record each block's rolling hash in a table.
      2. Slide a 16-byte window along the target one byte at a time, updating its hash cheaply, and look the hash up.
      3. On a hit, compare the real bytes, then extend the match backward and forward as far as source and target agree.
      4. Keep the longest match whose copy costs fewer bytes than writing it out. Emit the bytes skipped since the last copy as a literal, then the copy, and continue after it.

      A copy is kept only when its length is at least the digits of the pending literal's length, the copy's count and its offset, plus three opcode bytes. Fossil follows at most 250 entries of a hash chain. When the source is 16 bytes or shorter no copy can win, and an encoder MAY write the whole target as one literal. None of these numbers is visible in the delta.

      §6Security considerations

      • The checksum is a 32-bit sum. It catches accidental corruption but anyone can forge it. Integrity comes from the artifact's name, a cryptographic hash checked by the layer that stores it.
      • A parser MUST NOT read past the end of the delta, and integer reading MUST stop at the buffer's end. A zero-length delta is rejected before any read.
      • A failed application MUST NOT be reported as success. Callers MUST check the result and discard the output on failure.
      • Decoders SHOULD bound every segment by the declared target length rather than waiting for the trailer. The declared length is itself untrusted: constrained systems SHOULD check it against their own limits before allocating.
      • Bytes 0x80–0xFF MUST end an integer. A decoder that masks the high bit before looking up a digit accepts 64 extra digit bytes and parses crafted input differently from everyone else.

      App. CCollected grammar

      ABNF per RFC 5234. Payloads are located by count, which ABNF cannot express, so the count governs. Where the grammar and the prose differ on what a decoder tolerates, the prose wins.

      delta     = header *segment trailer
header    = integer LF
segment   = copy / literal
copy      = integer "@" integer ","
literal   = integer ":" payload
            ; <integer> opaque bytes; MAY contain LF;
            ; located by count, not by scanning
trailer   = integer ";"
integer   = 1*DIGIT64
DIGIT64   = %x30-39 / %x41-5A / "_" / %x61-7A / "~"
            ; value 0-9, A-Z=10-35, _=36, a-z=37-62, ~=63
payload   = *OCTET      ; exactly <count> octets
LF        = %x0A
