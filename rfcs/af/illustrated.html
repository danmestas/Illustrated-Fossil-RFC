The Fossil Artifact Format

Fossil keeps a project as a set of artifacts, each named by the hash of its own bytes. Some hold the contents of files. The rest are short text documents built from cards, and they record everything else: check-ins, tags, wiki pages, tickets. Here is a whole one, the root check-in from the draft's Appendix A.1.1.

A check-in manifest, card by card. Point at a token to read it.127 bytes · 6 cards · named by SHA-1
Six cards, one per line, in alphabetical order of their letters. The SHA-1 hash of these 127 bytes is the artifact's name.
card letter token checksum of the bytes above

§1–2What an artifact is

An artifact is an immutable byte sequence named by the cryptographic hash of its content. A repository's project state is the unordered set of artifacts it holds. The order they were added in does not matter, and two repositories holding the same set represent the same project state.

There are two kinds. A content artifact is any byte sequence, such as one version of a file. A structural artifact is a text document built from cards that records relationships among artifacts: a check-in, a wiki page, a ticket change, and five other types. Both kinds are named and stored the same way. A reader tells them apart by attempting a structural parse.

Artifacts are added but never changed or removed in normal operation. A name is a function of content, so an artifact received from any peer is identical to the same artifact held locally, and two repositories converge by exchanging the artifacts each lacks. The draft calls this a grow-only set. User accounts, settings and the map from names to local storage are local state, outside the artifact model. Content may be stored or sent as a delta, which changes neither its bytes nor its name.

The draft defines these terms for the whole Fossil suite: the Delta Format, Sync Protocol and Repository State drafts reuse them without restating them. It uses MUST, SHOULD and MAY in the BCP 14 sense, and only when capitalised.

§3Naming an artifact

§3.1The hash of the stored bytes

An artifact's name is the hash of its complete raw bytes, taken as one blob. Nothing is added before hashing, and nothing is canonicalised, re-encoded or stripped: the bytes hashed MUST be exactly the stored bytes. A signed artifact's stored bytes include its signature wrapper, so its name covers the wrapper too.

When content arrives together with a name, the receiver's storage step uses that supplied name as the candidate rather than computing a new one. Checking that the name matches the content is a separate job for the caller (§3.4).

§3.2Two algorithms, told apart by length

A name is either 40 hexadecimal digits, a SHA-1 hash, or 64, a SHA3-256 hash. A candidate of any other length MUST be rejected, and the length check comes before any check of the characters. The lengths never overlap, so the length alone says which algorithm made a name. Validation, verification and display all dispatch on it, and there is no other algorithm marker.

SHA3-256 here is the FIPS 202 function, with the 01 domain-separation padding, which differs from the original Keccak submission. Both are written as lowercase hexadecimal. Which of the two names newly stored content is the hash policy's choice (§7).

§3.3Lowercase, compared exactly

Every name an implementation computes or emits MUST be lowercase. A token with an uppercase digit is therefore not a valid name and can never verify. A parser MAY reject it when it validates the token, or MAY accept it there and let it fail verification later. The two choices interoperate because conforming data never contains one. A parser that accepts uppercase MUST NOT lowercase it.

Name some bytesUTF-8 text, hashed both ways

§3.4Verifying a name

Verification picks the algorithm by length, hashes the content, and compares the candidate byte for byte with the digest written in lowercase. A 40-digit name is checked against SHA-1, a 64-digit name against SHA3-256, and any other length never verifies. The caller sees one failure signal: a wrong length, a non-hex character and a digest mismatch look the same. When a receiver is handed a name:

  1. It parses the token as a name and selects it as the candidate storage name.
  2. Normally it rebuilds the full bytes, checks them against the name, and only then stores the artifact. If the check fails, the artifact MUST NOT be treated as verified under that name. The receiver makes this check; the storage step does not.
  3. Some paths store first and check later: a clone, and a delta whose source has not arrived yet. Being stored under a name is never proof that the name was checked.
  4. Storage then uses the name to find duplicates and to decide whether the repository must switch to SHA3 names (§7.4).

§3.6Looking up a prefix

Informative. Prefix lookup is a local convenience, not part of the format.

A lookup takes 4 to 64 hexadecimal characters and lowercases them, unlike the parse path. It then matches the prefix against all names without caring whether they are 40 or 64 digits long. If more than one artifact matches, the name is ambiguous, and a SHA-1 name colliding with a SHA3 name is reported the same way as two names of one kind.

§4Cards

A structural artifact is a sequence of cards. This section covers how a parser frames the bytes, removes a signature, splits lines and tokens, decodes escapes, enforces order and repetition, and checks each card's tokens.

§4.1Four gates before the first card

A parser MUST pass these gates, in this order, before it interprets any card:

  1. The input is not empty and its last byte is LF. This is checked on the raw bytes, so a signed artifact's outer wrapper must end in LF.
  2. Any signature wrapper is removed (§4.1.1). The stripped content also ends in LF, because the cut keeps the LF before the signature armor.
  3. Line 1 meets a stricter rule than other cards: the stripped content is at least 10 bytes long, its first byte is a letter A–Z and its second byte is a space. A first card with no arguments fails here, although argument-less cards are allowed later.
  4. The Z card checksum is verified (§6.2). A Z card that is present but wrong MUST cause rejection. A missing Z card passes this gate and is caught later by §5.2.

When the card loop ends, any bytes left over MUST cause rejection.

§4.1.1Removing a signature wrapper

A reader MUST remove both PGP clearsign wrappers and SSH signed wrappers before parsing:

  1. Stripping happens only when the first 34 bytes are exactly -----BEGIN PGP SIGNED MESSAGE----- or -----BEGIN SSH SIGNED MESSAGE-----.
  2. The body starts after the first blank line, found as LF LF or LF CR LF. That CR is the only CR the whole parse pipeline tolerates. With no blank line, nothing is stripped.
  3. A backward scan cuts the content at the first LF-----BEGIN PGP SIGNATURE----- or LF-----BEGIN SSH SIGNATURE-----, keeping that LF as the last byte. With no match, the content runs to the end.

The armor literals are 30 bytes but only 29 are compared, so an armor line one dash short, followed by any byte, also matches. A receiver that does not know the SSH prefix leaves it in place; the artifact then fails the line-1 gate and is treated as a content artifact.

The name, the card parser and the Z checksum each read a different stretch of the same bytes (§9). The name covers every stored byte, and so does signature verification when it is done. The parser reads the stripped content. The Z checksum covers the stripped content up to its final 35 bytes. Implementations MUST keep these apart: wrapper bytes never enter the Z checksum and always enter the name. A signed artifact and its unsigned inner content are two artifacts with two names.

§4.1.2Sterilization

Informative.

To make content deliberately unparseable as a structural artifact, a writer adds a first line starting with #, such as # Remove this line to create a well-formed Fossil artifact. It fails the line-1 gate. For signed content the marker goes just before the signature block, so the signature stays at the end. A fast well-formedness probe and a full parser SHOULD give the same verdict on every input.

§4.2Lines and tokens

card        = card-letter ( SP card-args LF / LF )
card-letter = %x41-5A                   ; A-Z; 21 letters defined
card-args   = token *( SP token )
token       = 1*tchar
tchar       = %x00-09 / %x0B-1F / %x21-FF   ; any byte but space and LF

The byte after the card letter MUST be exactly one space, when arguments follow, or LF. Anything else makes the card invalid, a tab included. Tokens split on space and LF only, so a tab is part of a token and a token can never hold a space. A CR is an ordinary token byte. One card is not one line: the W card's body may contain LF bytes (§4.7.18).

§4.2.1Exact arity

Each card's grammar fixes its maximum number of tokens as well as its minimum. A card with more tokens than its grammar allows MUST cause the whole artifact to be rejected: a second token on B, C, G, H, I, K, L, N, R, U, W or Z, a third on J or on the two-token Q, a fourth on A, a fifth on F. The same rule rejects bytes left after the last card.

§4.2.2A closed alphabet

Exactly 21 card letters are defined. A letter outside A–Z MUST be rejected, and so MUST the five unused capitals. There is no path for accepting unknown letters from a future version.

§4.3Escapes

Tokens that carry free text are escaped so they contain no space or LF. The decoder MUST recognise exactly eight pairs:

EscapeByteEscapeByte
\nLF (0x0a)\vVT (0x0b)
\sspace (0x20)\fFF (0x0c)
\ttab (0x09)\0NUL (0x00)
\rCR (0x0d)\\backslash (0x5c)

A backslash before any other character is dropped and the character kept, so \q decodes to q. A backslash that ends a token stays a backslash. Neither raises an error.

§4.3.1Which tokens are decoded

Decoding applies at exactly 12 token positions on 9 card letters. Hashes, checksums, timestamps and the W card are never decoded, so every token of B, D, E, G, I, K, M, P, Q, R, W and Z is read raw.

The A card target is the one hash-bearing position decoded before it is validated, because it may hold a wiki name instead (§4.7.2). Validation sees the decoded value, so a token full of escapes MAY decode to pure hex, and is then checked as a hash like any other.

§4.4Card order

Card letters MUST never decrease: each card's letter is greater than or equal to the one before. Equal letters may follow each other, which is how repeatable cards work. One exception is normative. An N card MAY follow a P card when the artifact has already shown a valid E card, which makes it a technote; a parser MUST accept that, and MUST reject every other out-of-order card. Appendix A.1.2 is such a technote. Two consequences:

  • B comes before F. By the time any F card is checked, the parser knows whether a B card exists, so it can decide in one forward pass whether F cards need a hash.
  • Nothing comes after Z. Z is the last letter, and the checksum framing fixes the Z card as exactly the final 35 bytes of the stripped content: Z, a space, 32 hex digits, LF. Being last is enforced by order plus byte position. The Z card's own grammar checks only its token.

§4.5Once, or many times

Twenty letters fall into two classes (§4.5.1). A duplicate of a single-occurrence card MUST be rejected: A, B, C, D, E, G, H, I, K, L, N, R, U, W. A repeatable card adds to a list: F, J, M, T, P, Q. Z is in neither. It has no duplicate check; an earlier Z line is simply content covered by the final checksum, which looks only at the last 35 bytes.

Runs of repeatable cards have their own order (§4.5.2):

CardWithin its run
FStrictly ascending by decoded filename. Equal or descending is rejected.
JStrictly ascending by field name.
MStrictly ascending by hash.
TAscending by name, then by target hash. Equal names need strictly increasing hashes.
PNot sorted or deduplicated. The order means something: primary parent first.
QNo order and no duplicate check.

The F check runs on the decoded name, after decoding. It is what lets a reader binary-search a baseline's file list and merge a delta manifest with its baseline (§8.2).

§4.5.3One comparator

The F, J, M and T checks, the merge walk and single-name lookup all compare the same way: raw bytes as unsigned values, with no locale, no Unicode normalisation and no case folding. A string sorts before any longer string that starts with it, an absent value sorts before any present one, and / is just byte 0x2f. Writers emit F cards in this same order. The R card's “filename order” (§6.3) is this order too.

§4.6Validity predicates

Three predicates check decoded tokens, treated as unsigned bytes.

Pathnames (§4.6.1) apply to the A card filename and the F card filename and old name. A parser MUST reject a name if and only if it is empty, starts with /, is . or .., starts with ./ or ../, contains //, ends with /, or has a path element that is . or ... Nothing else is checked: backslashes, spaces, control bytes and invalid UTF-8 all pass. A writer creating a new name is held to more. It MUST NOT emit a backslash, and MUST emit valid UTF-8 without overlong forms, characters above U+FFFF, surrogates, private-use characters U+E000–U+F8FF, or the noncharacters U+FDD0–U+FDEF and U+FFFE–U+FFFF. A validator of existing artifacts MUST apply only the parser rules.

Wiki names (§4.6.2) apply to the L card title and to an A card target that is not a hash. A parser MUST reject a name if and only if its first byte is 0x20 or below, a later byte is below 0x20, it has two spaces in a row, it ends with a space, or it is not 1 to 100 bytes long. Every byte from 0x21 up is otherwise allowed, with no UTF-8 check.

§4.6.3Reserved filenames

Some names belong to Fossil's own metadata. A decoded F card filename is reserved when:

  1. after removing one trailing -wal, -shm or -journal, compared without case,
  2. the rest ends, without case, in _FOSSIL_ or .fslckout,
  3. and that ending is the whole rest, or follows a /, or a suffix was removed in step 1.

x_FOSSIL_ passes. x_FOSSIL_-wal and dir/.fslckout-journal are reserved. An F card with a reserved name MUST be silently dropped from the file set; the artifact is still accepted. The sort check runs first, so the dropped card must still be in order, and the next F card is compared with the last card kept. In the reference parser the drop happens before the card would make the artifact a manifest. Only the current name is tested, never the old name.

§4.6.4Timestamps

D and E card timestamps are single raw tokens, never decoded. A writer emits YYYY-MM-DDTHH:MM:SS with an optional fraction, and for stored artifacts whose time can order repository state a producer MUST use that form. A reader MAY accept more: a date only, a time only (read as a time on 2000-01-01), the words now, subsec and subsecond, or a bare Julian day number greater than 0 and less than 5373484.5. A date-time may carry a timezone. The separator must be uppercase T; lowercase t is rejected.

Each field has an exact digit count: a 4-digit year, month 01–12, day 01–31 with no calendar check (2024-02-31 passes), hour 00–24, minute and second 00–59. A date MUST fall strictly after -4713-11-24. The relative words are resolved against the clock when parsed, so two ingestions of the same bytes can store different times. They are admitted for compatibility only.

§4.7.1Hash tokens

Every token that names an artifact MUST be exactly 40 or 64 hexadecimal digits, either case: the A target when it is a hash, the A source, B, the E identifier, the F hash, G, I, M, every P token, both Q tokens once the sign is removed, and the T target unless it is *. The K ticket identifier is the exception at 40 digits only; writers MUST emit it lowercase and parsers MAY accept either case. R and Z hold 32-digit MD5 checksums. None of these is decoded, apart from the A target.

§4.7.2A: attachments

An attachment artifact has exactly one A card. Its filename is decoded and MUST pass the pathname predicate; only the last path component is kept. Its target is decoded and MUST look like a hash or a wiki name, though the parser does not check that it names anything. The target is resolved later, when the artifact is crosslinked, in a fixed order: forum post, ticket, wiki page, technote. A target that names nothing known is still recorded, as a generic artifact reference, and is not an error.

The source decides the operation. With a source, the attachment is added. Without one, the attachment for that (target, filename) pair is deleted. The operation with the latest time wins.

§4.7.6F: files

In a baseline manifest every F card MUST carry a hash. In a delta manifest the hash MAY be left off; the card then marks the file as deleted from the baseline (§8.2).

The third token is always the permission and the fourth, when present, the old name of a renamed file. Producers SHOULD emit only w, x or l, and when they write an old name they MUST write a permission before it, normally w. A reader MUST accept any permission token without checking it: one containing x is executable, otherwise one containing l is a symbolic link, and anything else is a regular file.

§4.7.13P: parents

Zero or more hashes on one line. An empty P card MUST be accepted, because the initial empty check-in has historically had one; Appendix A.1.1 shows it. On a check-in the first hash is the primary parent and the rest are merge parents. On a wiki page they are prior versions; on a technote, one prior version with the same identifier; on a forum post, one prior version of the post. A producer SHOULD emit at most one P card. The ancestry graph and the branch, leaf and trunk views built from it belong to the Repository State draft.

§4.7.16T: tags

The tag name carries its sign: + applies a tag to one artifact, * applies one that propagates to descendants through primary children until blocked, and - cancels or blocks one. The name is decoded, and after the sign it MUST NOT be all hex digits, so it can never be mistaken for a hash prefix. The target is a hash, or * for the artifact carrying the card. A missing value is null, unlike J's empty string.

Parsing only checks syntax and order. The effects arrive when the artifact is crosslinked, and are the Repository State draft's business. Canonical artifacts use T *branch * NAME for a branch, T *sym-NAME * for a symbolic tag, and T +closed * and T -closed * to close and reopen a leaf.

§4.7.18W: a body counted in bytes

The W card is the one card that spans lines. Its token is a decimal size; the body starts right after that line's LF and is exactly size bytes, which may include LF or any other byte. The byte after the body MUST be LF. A writer MUST emit the size as plain decimal digits. A reader takes the leading digits of the token and ignores the rest, so 12x means 12. It MUST detect overflow, MUST check the size against the bytes that remain before reading the body, and MUST NOT scan the body for a card boundary.

If none appeared, the fallback decides: the artifact is a MANIFEST if it had a C card, any F entry or any P parent, and otherwise a CONTROL artifact. The legality checks of §5.2 then reject any artifact whose cards do not fit the type it ended up with.

§5.4Four checks per type

  1. A CONTROL artifact MUST NOT have a T card whose target is *.
  2. In a technote every T card MUST target * and use the + sign.
  3. A forum post MUST NOT have both an H card and an I card.
  4. A forum post's P card MUST NOT list more than one parent, since forum posts are not merged.

A forum post does not have to be consistent with other artifacts: following its I and P chains need not lead to the post its G card names.

§5.5A quick pre-filter

Informative.

A fast check may reject any input whose first card letter is N or later before trying a full parse. That is safe because every type's smallest allowed letter is M or earlier (MANIFEST B, CLUSTER M, CONTROL D, WIKI C, TICKET D, ATTACHMENT A, EVENT C, FORUM D), and order puts the smallest letter first.

§6Two checksums

Structural artifacts carry two MD5 checksum cards. The Z card covers the artifact's own text. The R card covers the content of every file in a check-in. Both are 32 hexadecimal digits.

§6.1Token grammar

At parse time both tokens MUST be exactly 32 hex digits, either case. Wherever a value is actually checked, the comparison is byte-exact against a lowercase digest, so in practice only lowercase passes. No artifact bytes are case-folded anywhere in the parse.

§6.2Z: the artifact checks itself

Let n be the length of the stripped content. A Z card fills its last 35 bytes:

OffsetBytesHolds
0 to n−36n−35everything above the Z card: the checksummed bytes
n−35, n−342Z and a space
n−33 to n−232the digest
n−11the terminating byte, which verification never reads

Verification MUST compute MD5 over the first n−35 bytes, write it as 32 lowercase hex digits, and compare it byte for byte with the stored digest. A present but different Z card MUST cause rejection. A missing one is not this step's concern; §5.2 rejects it. Because the comparison is exact, a digest with an uppercase digit MUST fail even when it is numerically right. Producers MUST emit Z, one space, the lowercase digest and LF. Existing implementations always verify; none can turn the check off.

Appendix A.2 works it through for the hero manifest above: the five cards before Z are 27, 22, 2, 35 and 6 bytes, so MD5 runs over bytes 0 to 91 and the Z card sits at bytes 92 to 126.

§6.3R: the check-in's files

A parser checks only that the R token is 32 hex digits. It MUST NOT be expected to recompute the value, and never does. The value is checked at commit time, against the working checkout, by the writer. An R card appears only in a manifest and is never required.

§6.3.2Computing R

One running MD5 is fed every tracked file in filename order, where filename order is the byte order of §4.5.3:

ctx = MD5-Init()
for each tracked file f, in filename order:
    MD5-Update(ctx, name(f))
    MD5-Update(ctx, SP || decimal(size-in-bytes(f)) || LF)
    MD5-Update(ctx, content(f))
r-value = lowercase-hex(MD5-Final(ctx))

The size is plain decimal with no leading zeros. So the checksum covers names and sizes as well as content. For Appendix A.3's three files the input is these 85 bytes, and its MD5 is the R card 95feb799536dc053e7968efb7cdd3ec3:

alpha.txt 12↵hello world↵beta.txt 23↵fossil artifact format↵gamma.txt 12↵R card test↵

An empty file set gives the MD5 of nothing, d41d8cd98f00b204e9800998ecf8427e, which is the R card of the root check-in in the hero.

§6.3.3R on a delta manifest

For a delta manifest, R MUST be computed over the full file set rebuilt from the delta and its baseline (§8.2), skipping delete markers, and not over the delta's own F cards. The writer emits R, a space, 32 lowercase hex digits and LF, nothing else (§6.3.4). An uppercase R card passes parsing but fails the commit-time check.

§7Hash policy

Each repository has a hash policy that decides which algorithm names newly stored artifacts, and whether the other algorithm may be consulted. It is local to the repository and only affects names assigned from then on.

§7.1Five values

Values MUST match exactly, case and all, and an unknown value is a fatal error.

ValueOrdinalNames new content withMay also consult
sha10SHA-1SHA3-256
auto1SHA-1SHA3-256
sha32SHA3-256SHA-1
sha3-only3SHA3-256nothing
shun-sha14SHA3-256nothing

The second algorithm is used to find out whether the same content is already stored under its other name. Under sha3-only and shun-sha1 a request for it MUST fail. Those two policies behave identically for local naming and differ only in what sync admits.

§7.2The default

A repository with no policy set MUST derive one. If it holds any SHA3 name, or no SHA-1 name at all, which includes an empty repository, the policy is sha3. Only when it holds SHA-1 names and no SHA3 names is it auto. The default is never shun-sha1.

§7.3Setting it

The policy is one stored configuration value. Nothing stops an operator setting it back to sha1. Asking for auto in a repository that already holds a SHA3 name silently stores sha3 instead, so once a SHA3 name exists, auto cannot be set again.

§7.4The ratchet

The rule: while the policy is auto, if the name storage is about to assign has 64 digits, the repository MUST switch to sha3 in the same write, before the artifact is looked up, inserted or linked.

Under auto, new content is named with SHA-1, so a 64-digit name arrives in only two ways:

  • incoming content carries a 64-digit name, or
  • local content's SHA3 hash matches an artifact already stored, and that artifact's 64-digit name is reused.

A name the receiver rejects before storage switches nothing. A name stored before it is checked does switch the policy.

§7.5One name per content

When content is stored without a supplied name, storage MUST first hash it with the other algorithm, where the policy allows, and look that name up. Only on a miss does it name the content with the primary algorithm. Under sha1, auto and sha3, local writes never give the same bytes two names. Under sha3-only and shun-sha1 the lookup cannot happen, so new content MUST get a SHA3 name even if the same bytes already have a SHA-1 name. Some content is then stored twice, and delta compression keeps the cost down.

§7.6Names never change

A name is assigned once, when content is first stored. Changing the policy MUST NOT rename or rehash anything already stored.

§7.7During sync

Peers do not negotiate a policy; each applies its own. The one signal that matters is the peer's announced version: if it predates SHA3 support, a sender refuses to send any artifact with a 64-digit name, with an explicit error. It never converts or silently skips it. What shun-sha1 does to incoming SHA-1 artifacts is defined by the Sync Protocol.

§8Rebuilding a delta manifest

A manifest with a B card is a delta manifest; one without is a baseline manifest. Nothing else decides it, not file count, not an R card. A delta manifest lists only what changed since its baseline, and anything that needs the full file set MUST merge the two. A delta manifest is a different thing from the Delta Format, which encodes an artifact's bytes one layer below. This merge works on cards.

Appendix A.4 has a baseline with three files and a delta that modifies one, deletes one and adds one:

§8.1What the merge needs

Both lists sorted by decoded filename. A conforming parser already guarantees that (§4.5.2). A delete marker is an F card with no hash, allowed only in a delta manifest.

§8.2The merge walk

An implementation MUST walk both lists at once in filename order, comparing decoded names byte by byte. At each step:

  1. Same name, and the delta entry has a hash: emit the delta entry. Both lists advance.
  2. Same name, and the delta entry has no hash: the file is deleted. Both advance and nothing is emitted.
  3. Different names: emit whichever sorts first and advance only its list. A delete marker for a name the baseline lacks is emitted here too, but it adds no file. It is not an error.

The walk ends when both lists are used up. When one ends first, the rest of the other is emitted as it stands, delete markers included. So anything computed from the result MUST skip entries with no hash, as the R card computation does.

§8.3Finding the baseline

The baseline is loaded the first time it is needed. If it is missing or is not a manifest, file enumeration and single-name lookup MUST treat that as fatal. Consumers that can wait, such as a parent-to-child file diff or post-parse relationship processing, MAY instead record the gap, keyed by the dependent artifact and the missing hash, and retry when the baseline arrives. Each step of an enumeration reports no error for a missing baseline; it quietly lists the delta alone. So implementations MUST resolve the baseline before they start.

§8.4Looking up one name

To find one file in a delta manifest, an implementation MUST search the delta's own F cards first, with closest-name matching turned off. A delete marker for the name means not found, without asking the baseline. Only a name the delta does not mention at all sends the lookup to the baseline.

§8.5A view that does not merge

Informative.

The JSON rendering of a manifest lists its own F cards, so for a delta manifest it shows only the changes. This is deliberate, and that view is the one exception.

§9Security considerations

  • A name binds content only as strongly as its hash. SHA-1 has known collision attacks; SHA3-256 does not, and is the default for new artifacts in most repository states. Existing implementations compute SHA-1 with collision detection, and shun-sha1 lets a repository refuse SHA-1 artifacts arriving by sync.
  • MD5 is not collision-resistant. The Z and R cards catch accidental corruption. Protection against a crafted artifact comes from its name.
  • Name, Z checksum and signature each cover a different byte range (§4.1.1), and implementations MUST keep them apart. A wrapper says how the bytes are laid out, nothing more. It is not evidence that a signature was checked or that the signer is trusted; the draft leaves signature checking out of scope.
  • A receiver that admits content as verified under a supplied name without checking it breaks the integrity of everything downstream. Content stored under an unchecked name MUST NOT be treated as verified.
  • Name and digest comparisons are exact lowercase. Accepting a token at validation MUST NOT be taken as evidence of integrity.
  • The reserved-name drop changes the file set without failing the parse. Two readers disagree about such a manifest only if one skips the drop.
  • The W body is found by count. A reader MUST bound the size against what remains, reject overflow, never scan the body, and never read past the end of the buffer.
  • An earlier Z line is just content. Tools that scan text for a Z card can be fooled; verification MUST use the byte position of §6.2.
  • Rebuilding a delta manifest or verifying an artifact needs the artifacts it refers to. Until they arrive the reference stays unresolved, and the Sync Protocol says how to ask for them.

App. CWhere older documentation differs

These statements in Fossil's documentation, or in text that comes with existing implementations, do not match the body of the draft. The body is definitive.

Older text saysThe draft says
A manifest requires C, D, U and Z.It requires only D and Z; C and U are optional, for historical artifacts (§5.2).
Every type except a manifest needs a Z card.Every type needs one, manifests included (§5.2).
A wiki artifact with no U card counts as user nobody.It is rejected. A U card with an empty login reads as anonymous (§4.7.17).
A forum post whose G card does not match the root reached through its I and P chains is invalid.No parser enforces that, and the draft does not require it (§5.4).
The timestamp separator is a lowercase t.Only uppercase T is accepted (§4.6.4).
Only PGP clearsign wrappers exist.SSH signed wrappers are removed too (§4.1.1).
The J card's field name and value are both escaped.Only the value is decoded. Implementations differ here (§4.7.8).
(Implementations) One does not decode the N mimetype; one decodes the J field name.The decode map of §4.3.1 is the rule.
(Parsers) An N card is accepted right after P once an E card has made the artifact a technote.That exception is part of the ordering rule. Every other out-of-order card is rejected (§4.4).
(Implementations) One accepts any F permission token, one only w, x or l.Readers accept any token in third place; producers SHOULD write w, x or l (§4.7.6).
(Implementations) One joins repeated P cards, one rejects a second.Producers SHOULD emit one; receivers are not constrained further (§4.7.13).
