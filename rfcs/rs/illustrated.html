Fossil Repository State

A Fossil repository stores only immutable artifacts. Branches, tags, leaves, closed markers and the current trunk are not written down anywhere: every repository computes them from the artifacts it holds. This reading walks through those rules and shows each derived table beside the section that defines it, read from this draft's own repository.

§1Facts no artifact records

Every check-in, tag and edit is an artifact: a run of bytes named by its own hash, never changed once written. History is the append-only set of those artifacts. That gives strong integrity, but some everyday questions have no artifact that answers them. Which check-in is the latest on trunk? Which branch does a check-in belong to? Which leaves are still open? What does a tag point to now? (§1)

Each answer is implied by the whole set. A repository works it out by reading the parent links and tag records spread across the artifacts. The draft calls the result the repository's state: the check-in ancestry graph, branch and tag membership, open leaves, closed markers, and the check-in a symbolic name selects. The rules are fixed so that two independent implementations reading the same artifacts reach the same answers (§1).

One answer has a local input. The current trunk also depends on the repository's main-branch setting, so two repositories with the same artifacts can name different current-trunk check-ins when that setting differs (§1, §9).

§1.1What this draft covers, and what it borrows

The scope is the meaning computed from parent and tag cards (P and T cards): ancestry, branch membership, named and symbolic references, leaves, closed markers and current-trunk resolution. The companion drafts supply the rest (§1.1):

DraftSupplies
Artifact FormatThe byte grammar of P and T cards, hash formats and lengths, content-type rules, hash-to-check-in resolution, delta-manifest reconstruction.
Delta FormatOnly the content-delta encoding underneath.
Sync ProtocolHow artifacts move between peers. The state rules hold however the artifacts arrived.

Ordering uses the numeric event.mtime and tagxref.mtime values derived from artifact timestamps. Results are reproducible only when the stored D-card timestamp names a fixed instant. The compatibility literals now, subsec and subsecond fall outside the reproducible rules (§1.1).

§3Building the check-in DAG

Each check-in manifest names its parents in its P card. An initial check-in has an empty P card; a merge names several. A reader turns every parent reference into a parent/child linkage record once and walks those records afterwards, instead of re-parsing manifests on every query (§3).

§3.1One row per parent and child

Each linkage row is keyed on the pair (parent-id, child-id) and carries a flag saying whether the parent is primary, the check-in's modification time, and a baseline id used for delta-manifest reconstruction (§3.1). The pair is unique. A manifest MAY name the same parent twice, since the Artifact Format does not require P-card references to be sorted or deduplicated, and the table keeps a single row for the pair (§3.1).

Section 7.1 names this table plink. Its columns map directly: pid and cid are the pair, isprim is the flag, mtime the time, baseid the baseline.

§3.2Primary parent and merge parents

Exactly one linkage row per child has the primary flag set: the row for the first hash on the P card. Every other parent gets a row with the flag unset, marking a merge parent. A sole parent is primary. When a P card repeats a hash, the row keeps the flag chosen by that hash's first appearance (§3.2).

A reader MUST treat the primary row as the mainline ancestor for linear-history operations such as first-parent traversal and the timeline's mainline. Merge rows MUST be included when full ancestry is needed, for a merge base or an ancestor test, and MUST NOT be treated as the mainline predecessor (§3.2).

§3.3Walking both ways

Edges run from parent to child. Manifests name their parents by hash and never change, so an edge's direction is fixed when it is written (§3.3). The same rows serve both walks: toward the origin through an index on (child-id, parent-id), and toward descendants through the (parent-id, child-id) key. There is no separate ancestor or descendant store (§3.3).

§4Crosslinking

Crosslinking is the step that reads a stored artifact's cards and turns them into repository state. T cards are validated first, then routed into tag and branch state (§4).

§4.1Checking T cards

A T card holds a tag name, an artifact hash or the self-tag marker *, and an optional value. Before any effect is applied (§4.1):

  • The name MUST start with -, + or *: cancel, singleton or propagating.
  • Without that prefix, the name MUST NOT be all hexadecimal digits, at any length, so it cannot be mistaken for a hash.
  • T cards in one manifest MUST be strictly ascending by name, then by hash.
  • A hash field of * makes a self-tag, which applies to the manifest being parsed.
T *branch * feature          propagating, self-tag, value "feature"
T *sym-feature *             propagating symbolic name, self-tag
T -sym-trunk *               cancel the inherited sym-trunk

These three cards are in ascending order whether or not the prefix character counts toward the name. A manifest that fails any check MUST be rejected whole: no partial tag state comes from an invalid card set (§4.1).

§4.2The crosslink procedure

Once its T cards are valid, the crosslink step applies the manifest (§4.2):

  1. Target. A self-tag targets the artifact being crosslinked. Otherwise the hash is resolved to an rid. A hash not yet stored resolves to a phantom, an rid with no content. The effect is recorded against it and shows once the artifact arrives. A missing parent in the DAG is handled the same way, not as a fatal error.
  2. Applicability. The loop that applies tags, one tag write per card, runs only for control, manifest and event artifacts.
  3. Clusters. A cluster gets an implicit singleton cluster tag outside that loop, whatever T cards it carries.
  4. Propagation. If the check-in has a resolved primary parent, the parent's tags MUST be propagated again from the parent (§5.4). Every tag applied to a resolved target also MUST start a propagation walk from that target, with singletons first turned into cancels (§5.3).
  5. Idempotency. Crosslinking again MUST NOT add another linkage or event record. Fossil checks whether it has already recorded the manifest's file changes, and skips it if so. A manifest with no parent and no files has nothing to record, so the check cannot see it, but running again still leaves a single timeline row. Other markers are allowed if the stored result is the same. Steps 1 to 4 still run.
  6. Batching. Crosslinks MAY run as one batch in a single transaction. At the end, singleton reparent operations recorded during the batch are applied again, so a parent changed mid-batch ends up in the final state.

§4.3Rejection

The three syntax checks of §4.1 are the rejection list: no prefix, an all-hex name, or cards out of order. A manifest that fails one gets no tag writes, no propagation and no linkage at all (§4.3).

§4.4Artifacts a parser cannot classify

A conforming repository can hold artifacts a conforming parser declines to classify. The Artifact Format's required-card rule is one cause, and the reference repository has instances of it (§4.4). The draft separates two failures:

The artifactRepository state
Hashes to its name, but cannot be classifiedStored correctly. Assembly MUST NOT fail. The artifact is opaque: no linkage, no tags, no branch membership, as if it were a non-participating type.
Does not hash to its nameAn integrity failure. An implementation MUST reject it.

Diagnostics SHOULD tell the two apart. Calling a classification failure damage sends the operator after a defect the verified hash has already ruled out (§4.4).

§4.5How crosslinks read in comments

Generated comments fold some card combinations into one edit. A *branch card reads as “Move to branch”, and its paired -sym- and *sym- cards are folded silently into it. On their own, those two read as “Cancel tag” and “Add propagating tag”. This is presentation only; tag state is unchanged (§4.5).

§4.6Writing a tag

A tag or antitag starts as a control artifact with exactly one T card, T <c><prefix><name> <uuid> [value], where the leading character follows the tag type. The artifact is stored and then crosslinked like any other, and its card is checked by the same rules (§4.6).

§5Tag types and propagation

§5.1Three types

PrefixTypeValueEffect
-cancel0Removes or blocks a tag's effect.
+singleton1Applies to the target only.
*propagating2Applies to the target and carries forward along its primary children.

Any other leading character MUST be a fatal crosslink error (§5.1).

§5.2Where tag state lives

Tag state is the tagxref table, unique per (artifact, tag). Each row holds the tag type; srcid, the artifact whose T card applied the tag, or zero when the value was propagated in from an ancestor; origid, the artifact that originally holds a propagating tag; the value; an mtime; and rid, the artifact the row describes. Because (rid, tag) is unique, an artifact has at most one live entry per tag, and later writes replace earlier ones (§5.2).

When history is a single line on trunk, only the first check-in has direct rows, because it carries the branch and sym-trunk cards (§6.1). Every later row has srcid 0, origid pointing at the first check-in, and the first check-in's mtime, not its own (§5.4 step 4).

§5.3Applying a tag directly

  1. If the (tag, artifact) row already has an mtime at or after the incoming one, the write MUST be skipped. A strictly later time wins. With exactly equal times, the winner depends on write order and is implementation-defined.
  2. Otherwise the row is replaced: the raw type from the card, srcid the artifact carrying the card, origid and rid the target.
  3. A cancel clears the value to null.
  4. Before propagation, a singleton is downgraded to a cancel. It never passes its value on, and it blocks a same-named tag from propagating through it. A propagating tag passes unchanged.

§5.4Propagation

Propagation carries a tag from an artifact to its descendants along primary links only. It MUST NOT follow merge links, so a tag reached only through a merge has no effect past the artifact it names (§5.4). The walk accepts only type 2 or type 0 and MUST reject anything else.

In the figure, c1 and f1 carry direct branch tags. Trunk's tag walks c2 to c5 along primary links. It does not enter f1, whose own row is direct. Feature's tag reaches f2, and the dashed merge into c5 carries nothing. f2 has a child, but on another branch, so it is still a leaf of feature (§2).

  1. Seed a priority queue, ordered by mtime, with the starting artifact.
  2. Take an artifact from the queue and list its primary children.
  3. A child qualifies only if its row has srcid 0 and an mtime strictly earlier than the tag's. A nonzero srcid or an equal or later time keeps the existing row. A child with no row qualifies for type 2 but not for a cancel, so a cancel stops where there is nothing to delete.
  4. Type 2 replaces the child's row with type 2, srcid 0, the origin's origid, value and mtime. Type 0 deletes the child's row.
  5. Each child that changed joins the queue.
  6. The walk ends when the queue is empty.

§5.5What stops a propagating tag

  • A direct same-tag row, srcid nonzero, stops it whatever that row's time. The time comparison applies only to inherited rows.
  • A cancel for the same tag deletes any propagated row there and keeps the value from that artifact's primary children.
  • A singleton never propagates. Downgraded to a cancel, it blocks just as a - card would.

The draft calls this the complete definition of “propagation until blocked” for the whole document set (§5.5).

§6Branches

§6.1The branch of a check-in

Every check-in belongs to exactly one branch. An implementation MUST find it from a tagxref row for the branch tag on that check-in with tagtype above zero; the row's value is the branch name. A check-in with no such row belongs to the default branch (§6.1).

That fallback is narrow. In a conforming repository the first check-in of every branch, the initial check-in included, carries the propagating branch tag and a matching propagating sym-<branch> tag, and later check-ins inherit both. Creating a branch MUST create the sym- marker, without which the name would not resolve. A check-in attributed to the default branch only by the fallback is not thereby its resolvable tip or its open leaf (§6.1).

The default branch name is the main-branch setting, or trunk when it is unset. An implementation MUST read the setting and MUST NOT assume a fixed string when one is set (§6.1).

§6.2Creating a branch

A new branch is two propagating cards on its root manifest: *branch with the new name as value, and *sym-<name>. Both propagate under §5, which is how later check-ins inherit the branch (§6.2). The root MUST also cancel the inherited propagating sym- tags with - cards, so it does not carry the parent branch's names alongside its own. The branch new command goes further and cancels every active sym- tag it sees (§6.2).

Creation MUST NOT succeed when the name already names an open branch, and the check MUST happen before the root manifest is written. Fossil's own reuse guard is narrower than §9's open-leaf test: it looks for a propagating branch tag with that name and excludes only a singleton closed marker (§6.2).

§6.3Listing branches

The branch list is derived. Group the tagxref rows where tag.tagname = 'branch' and tagtype > 0 by value: each value is a branch, with its greatest event.mtime and the count of its check-ins (§6.3).

The listing's open or closed column checks only the branch's representative check-in, the member with the greatest event.mtime. That can disagree with §9, which calls a branch open when any open leaf remains. If the newest check-in is closed while an older leaf is still open, the listing says closed and §9 says open. The draft says neither is in error: they answer different questions (§6.3). The list can be filtered by state, private status, name glob and merged status, and ordered by name or time (§6.3).

§6.4The current branch of a checkout

Some Fossil code paths read the branch tag's value on a checkout without the tagtype > 0 filter. The draft calls this a textual inconsistency, not a second rule. A conforming implementation MUST apply the filter everywhere, including when it reports a checkout's current branch (§6.4).

§7Leaves

§7.1The leaf table

A leaf is a check-in with no child on the same branch. The set can be computed by joining plink and tagxref, but implementations keep it in a leaf table of one integer column. The table carries no open or closed flag; that is derived separately (§7.1).

§7.2The normative test

A check-in is a leaf if and only if no plink row naming it as parent has a child on the same branch. The test MUST NOT distinguish primary from merge links: a same-branch child reached only by a merge still makes its parent a non-leaf (§7.2). A narrower primary-only child count MAY exist for other uses, and documentation calling it “zero children of any kind” MUST NOT be read as the leaf test (§7.2).

§7.3Keeping the table right

  • Full rebuild. Recompute the table from every check-in, dropping those with a same-branch child. A check-in with no parent at all is included when it has no same-branch child. Fossil's leaf_rebuild() takes candidates from plink child ids, so this is a deliberate normalisation. Reserve it for explicit rebuilds.
  • Incremental check. For one check-in: remove it if it has a same-branch child, otherwise insert it, tolerating a row already present.
  • Deferred scheduling. When a parent link is created or a branch tag applied or propagated, schedule a recheck of the check-in and each of its direct parents.
  • Batch application. Run every scheduled recheck and clear the schedule before the table is trusted. A commit's leaf changes become visible here.

§7.4Open and closed

A leaf is open if and only if it is in the leaf table and has no active closed row, meaning a tagxref row for the closed tag whose type is an assignment. Implementations MUST offer the test as an existence expression, which callers can negate to select open leaves, and as a check on one check-in (§7.4).

§7.5More than one open leaf

The open leaves of a branch are the leaf-table members that are not closed and share the branch. To decide whether a check-in is an ambiguous leaf, an implementation MUST first confirm it is a leaf, and if so test for at least one other open leaf on the same branch. The test reads the leaf table, so a table that has drifted gives wrong answers even when plink is correct (§7.5). A report of ambiguity SHOULD list every open leaf on the branch, newest first, with hash, time and rid, and mark the one the checkout is on (§7.5).

§7.6When to re-evaluate

Leaf status MUST be re-evaluated when a branch tag is applied directly to a check-in, and for every descendant that gains or loses a propagating branch tag. Both go through the deferred schedule (§7.6).

§7.7Leaves are not names

Leaf enumeration asks which check-ins have no same-branch descendant and whether any are open. Name resolution asks what a name refers to. A resolver MAY consult the leaf table, but the leaf table's rules MUST NOT be conflated with a resolver's precedence rules (§7.7).

§8Resolving a name

§8.1One name, one check-in

Name resolution turns a branch name, tag name or reserved keyword into a single check-in: the one carrying the active tag with the greatest event.mtime. It answers even when that check-in is closed, not a leaf, or both (§8.1).

§8.2The rule

For a plain name N, resolution MUST pick the check-in with an active sym-N tag and the greatest event.mtime. This is the last fallback, and it either succeeds or fails outright. Closed status and leaf status MUST NOT affect the choice: the query joins tag, tagxref and event data and nothing else (§8.2).

An implementation MAY first look at only the thirty most recently modified candidates, provided the result is identical to a full scan. When two candidates share the greatest time exactly, the query engine's row order decides and the result is implementation-defined (§8.2).

Type a branch or tag name. The tool runs the §8.2 query and, beside it, the §9 open-leaf query for the same name, so you can see when the two questions part.

A fraction is padded to three digits with 9s and, unless it is already .999, advanced by one millisecond. The deprecated local: form skips the expansion and hands its text to julianday(). A portable timestamp MUST use YYYY-MM-DDTHH:MM:SS[.fraction]Z. If nothing matches and the name ends in exactly one punctuation character, resolution MUST retry without it, so a name lifted from prose or a URL still resolves. A request for a branch type is rewritten to check-in type, and the result is moved to the branch's first check-in by the branch walk (§8.3).

§8.4The branch walk

root:, start:, merge-in: and branch-type requests share one walk: from the resolved check-in, follow primary parents toward the root, watching whether each ancestor still carries the same active branch tag. “Earliest still on branch” returns the last ancestor that does; “first ancestor off branch” returns the first that does not. It is a parentage walk, not another tag-and-mtime selection (§8.4).

§8.5When the name and the leaves disagree

Take a branch BR with an open, childless C1 at time T1, and a later C2 at T2 that is closed but carries the active sym-BR. Resolving BR MUST return C2. Open-leaf enumeration skips C2 and surfaces C1. Callers MUST NOT substitute one question for the other (§8.5). Section 10.2 shows this happening in a real repository.

§9Current trunk and forks

The current trunk is the main-branch name run through §8, with no special case. The setting is local: not an artifact and never synchronised. Everything after the name is artifact-derived, so current-trunk is a function of the artifact set and the local setting together. Two repositories with identical artifacts can disagree on it (§9).

A branch MAY have more than one leaf, and is then forked. Resolution against a forked branch neither refuses nor raises an ambiguity error; it returns the candidate with the greatest mtime (§9).

Whether a branch is open is a separate question. A check-in is the branch's open leaf, and implementations MUST treat it as such, only when all three hold (§9):

  • it carries an active branch tag whose value is the branch name;
  • it is in the leaf table;
  • it has no active closed tag.

A branch is reported open, with an open-as-of date and a short id, exactly when such a check-in exists. If a report must name one of several open leaves it MUST pick the one with the greatest mtime (§9).

A branch's merge target is read by following at most one plink edge from its representative check-in to a child and taking that child's active branch value. A branch has at most one merge target. When the representative has several children, the draft leaves the choice implementation-defined (§9).

Ties are left open on purpose. When candidates share the greatest mtime to full precision, an implementation MAY return any of them, callers MUST NOT rely on which, and two implementations MAY differ. The draft declines to add a tie-break by hash or id (§9).

§10Worked example: a fork with a closed leaf

Two repository states in which leaves and name resolution see the same graph differently. In both, closed status filters the default leaves view but does not change what whatis and update pick for trunk (§10).

§10.1The closed leaf is the older one

Trunk forks after c4, leaving two trunk leaves and one feature leaf. leaves lists the open trunk leaf 4167aef42f and the open feature leaf 210d9276e4 and omits the closed trunk leaf 7aa867c048. leaves --all adds it back. The closed check-in is still a leaf and still on trunk. whatis trunk and update trunk both give 4167aef42f. Closed status changed the leaf list but not what trunk resolves to (§10.1).

§10.2The closed leaf is the newer one

Now the open leaf b05cbea82b is older than its closed sibling ee3a7eed71. leaves lists only b05cbea82b; leaves --all lists both, newer first. Yet whatis trunk reports ee3a7eed71, and update trunk moves the checkout from b05cbea82b to ee3a7eed71 (§10.2).

§10.3What follows

Tooling that needs the target of update or whatis MUST resolve the name directly, not infer it from leaves output (§10.3).

§11Security considerations

  • Crosslink state is computed locally and is never transmitted, negotiated or authenticated on its own. Tag and parent claims are whatever the artifact's producer asserted, so the state is only as trustworthy as the artifacts admitted (§11).
  • Implementations MUST treat it as derived data with no trust of its own, and MUST NOT give a tag or parent claim more weight than artifact admission already gave it. Crosslink state from an artifact that admission would reject MUST be rejected or discarded (§11).
  • The trust boundary is artifact admission, so the draft adds no separate mechanism. Weak admission checks weaken the derived view; correct ones bound it (§11).
  • Implementations SHOULD recompute the state from the admitted artifacts instead of caching it across changes, so a rejected or retracted artifact drops out without separate revocation logic (§11).
