draft-fossil-sync-protocol-00 · an illustrated reading

The Fossil Sync Protocol

Every Fossil repository is a set of hash-named artifacts that only grows. Sync gives each side what the other lacks, over ordinary HTTP POSTs, until neither has anything left to ask for. Each message is a list of short text lines called cards. This reading follows the draft section by section and replays a real clone of its own repository, one round at a time.

§1What sync does

A repository holds artifacts named by their hash, and the set only ever grows. Two repositories sync by exchanging the difference between their sets, so both end up with the union. It does not matter which side starts or when, because a union of grow-only sets comes out the same in any order (§1, citing the G-Set literature).

A repository can know an artifact's hash without having its content. The draft calls such a hash a phantom. Sync works in rounds: each round announces artifacts, turns unknown hashes into phantoms, asks for phantoms, carries content, and goes again while §3.7 says there is still work to do.

The client drives everything. It sends an HTTP request, reads the reply and decides whether to send another. The server keeps no state between requests (§1).

To see the rounds play out, watch a sync: a real pull or push between two copies of this draft's repository, animated message by message.

The draft covers transport, login, artifact and unversioned-file transfer, clone, configuration framing and termination. It leaves out how rows of the /user, /reportfmt, /shun, /concealed and /subscriber table groups are serialised, and implementations MAY omit those groups. Leaving out the /shun group does not remove the repository's local shun set, which still filters requests and admission (§1, §3.3, §7.7). Sections 3 to 11 are normative.

§3The sync loop

The client sends one HTTP request body full of cards. The server handles that body on its own and returns one reply body of cards. The client reads the reply and uses it to build the next request, if there is one. No card says “done”. A round ends when its body is used up, and the session ends when §3.7 finds no reason for another round. The loop has four parts (§3):

  1. Build the request. Start with login, version and the chosen operation, add remembered state such as the cookie, add the cards the last reply called for, and end with random bytes.
  2. Exchange cards. igot announces artifacts, gimme asks for missing ones, file and cfile carry content. The unversioned-file cards run the same announce, ask and send cycle for unversioned files.
  3. Repair phantoms. A side that learns a hash without its content records a phantom, and later rounds ask for eligible phantoms.
  4. Decide whether to continue. After reading the reply, the client counts the round and applies §3.7. New work drives another round. The server never acknowledges anything.

§3.1What a round carries

Every request MUST contain pragma client-version, and it MUST come before any card that asks for content, so the server can apply the SHA3 gate (§7.6) when it handles them. A body login comes before it. So does pragma send-private in the first round of a private sync, though later rounds put it after. The first round of a clone sends no login of either kind.

Push, pull and sync requests repeat push, pull or both in every round. A clone starts with clone 3 1. A request MAY also carry gimme, content, igot, configuration and unversioned cards, and the returned cookie, and it MUST end with a random comment. A normal reply ends with a # timestamp comment. Replies cut short before or during dispatch can leave that comment out.

§3.1.1How the client reads a reply

After undoing the transport encoding, the client takes the reply's cards in order:

CardWhat the client does
push, pullRecords the peer's servercode and projectcode. Its own operation stays the same.
igotApplies the phantom rules of §3.3.
file, cfileStores content per §7. Sets content-received only if content was stored or a dangling delta created a source phantom.
gimmeNotes that the peer lacks the artifact. If push is still on, the client holds the content and policy allows, it appends the content to the next request.
uvigot, uvfileRuns the unversioned-file state machine (§8.5.1, §7.3). A uvgimme in a reply is the wrong direction (§5.2).

error, cookie, #…Applies §10.1, replaces the stored cookie, or applies the comment rules of §5.3.

When the loop over cards ends, the client counts the round, evaluates §3.7, and only then throws away the state it kept for that round.

§3.2What each side remembers

Table 1 of the draft lists the client's state by how long it lasts. The project code, the phantom set and the cookie persist in the repository. The peer's version and date, the clone sequence number, the round number and the unversioned send table last for the session. Some flags live for one round only: whether an igot created a phantom, whether content arrived, which hashes the peer has or lacks, and the unversioned and private counters. Round state is reset when a round starts and kept until §3.7 has been evaluated. The server keeps its repository plus a few things scoped to one request, such as whether it already sent the unversioned catalog.

Cards for the next request are collected while the reply is still being read. The file and delta counts that §3.7(b) checks are the content cards collected in that window (§3.2).

When cookie login is in use (§6.5), the login travels in the HTTP Cookie: header and the body has no login card. A clone that the server refuses for lack of Clone permission gets a push card and then an error, with no cfile or clone_seqno (Table 3).

§3.3How phantoms are born and die

An igot HASH creates a phantom only if the receiver lacks HASH and can get it in the current direction: pull, clone, or receiving a push. A delta whose source the receiver lacks creates a phantom for that source.

In each round the client tracks which hashes the peer has announced or sent and which it has asked for. New phantoms can be requested at once. The scan for phantoms to request skips hashes the peer lacks, hashes in the shun table, and private hashes unless private sync is on. A shun-sha1 policy does not by itself suppress a gimme.

On gimme HASH, a side that holds the content sends it now or in a later message, if the direction and policy allow. If the direction forbids sending, it sends nothing and no error, and does not defer. If it lacks the content, it skips the request silently.

Storing the content deletes the phantom. A delta whose source is missing is kept under its own HASH, its phantom is deleted, a phantom is created for the source, and content-received is set. HASH is not requested again. The target can be rebuilt once its source chain arrives (§3.3, §7.4).

§3.4Clone uses the same loop

A modern clone runs the ordinary loop and §3.7, sending clone 3 SEQNO while it transfers and requests with no operation card after the sequence reaches zero. §8.1 to §8.4 hold the rules.

§3.5Pragmas

Pragmas are ordinary cards that keep their place in the body. Unknown pragma names MUST be ignored. §9 defines the known ones.

§3.6The cookie card

A server MAY send cookie TEXT. The client MUST replace its stored value with it and MAY send it back later. Servers MUST NOT depend on it and MUST tolerate cookies they did not issue and more than one cookie. Clients need not return one. This card is part of the body and is separate from HTTP cookie login (§4.3, §6.5).

§3.7When to stop

After reading a reply and counting the round, the client MUST send another round if and only if one of these holds:

LimbAnother round when
(a)A file or cfile stored content (a dangling delta counts), or an igot created a phantom, and the phantom table is still not empty. This applies to every operation.
(b)While reading this reply, the client appended at least one full or delta content card to the next request, or the unversioned upload phase is selected.
(c)This request sent a private igot HASH 1 and the round number is now exactly 1, or the reply's server-version made private inventory eligible and the client appended at least one such igot.
(d)This request sent a uvgimme and either the reply carried a uvfile or the round number is now below 3, or reading this reply appended a uvgimme.
(e)The operation is a modern clone, none of (a) to (d) fired, and this was the first clone round, or content was stored this round, or the sequence is still positive and the count of received artifact cards went up.

A positive clone sequence on its own does not keep a stalled session going. Remaining phantoms on their own MUST NOT cause another round or an error. If nothing holds, the client stops, and the server sends no completion card. If a round is needed but clone reissue is barred, the client sends the cleanup request of §8.2.

§3.8The client as a state machine

The draft restates the loop as five named states, in the style TCP uses. Where the state machine and a controlling section differ, the section wins. The round counter starts at zero just before the first request and goes up only after a reply has been read.

A first clone round sends no login and no configuration or unversioned hash, and it ignores any error in the reply. It always moves to EXCHANGE, which forces a second clone round. In EXCHANGE, an unknown or malformed reply card logs a local warning and ends only that reply's card loop. What was already parsed stays in effect, and §3.7 is evaluated as usual (§3.8, Table 5).

§3.9A narrow tolerance

Receivers tolerate only the cases the draft names: unknown pragmas, extra tokens on a few cards, one byte after a config payload, other whitespace between tokens, foreign cookies, errors in the first clone reply, and tokens beyond the sixth. The draft deliberately rejects the TCP habit of liberal acceptance, on the grounds that guessing at malformed input lets implementations drift apart. Fossil's tokenizer exposes at most six tokens per line, so senders MUST NOT emit a seventh, and receivers ignore any they find.

§4Transport

Sync is an HTTP POST to the repository URL, unchanged, with an empty path sent as /. Fossil's own client sends HTTP/1.0. Clients MUST NOT append /xfer. A request typed application/x-fossil or application/x-fossil-debug reaches sync whatever its path, and a request that is not a POST is redirected to the home page. Every request MUST carry an exact Content-Length and has a non-empty body. A reply MAY omit it, and Fossil then reads to end of file. Fossil ignores Transfer-Encoding. Over SSH the request adds X-Fossil-Transport: SSH.

  • Redirects. Follow at most 19 redirects with status 301, 302, 307 or 308; the twentieth is fatal. Never go from HTTPS to HTTP, and never redirect SSH or local-file transports. Strip any trailing /xfer from the target and change nothing else in the path. The client resends the same card body with fresh compression, headers and login for the new target. It does not reset peer state or choose cards again.
  • Status. Only HTTP 200 counts as a protocol reply. Any other status aborts before card parsing.
  • Content type of the reply. A missing type means compressed application/x-fossil. A value is matched case-insensitively by prefix: application/x-fossil-debug or -uncompressed selects the uncompressed body, any other application/x-fossil prefix selects compressed, and any other value is rejected. On the server, only the exact type application/x-fossil selects decompression of the request body.

§4.1Compression and media types

Media typeBodyUsed for
application/x-fossilCompressed containerAll production requests and ordinary replies.
application/x-fossil-debugPlain cardsDiagnostics only. It MUST NOT be used in production.
application/x-fossil-uncompressedPlain cardsClone version 3 replies. The cfile payloads inside are already compressed.

The compressed container is a 4-byte big-endian count of the uncompressed length, followed by a zlib stream: a 2-byte header, a DEFLATE body and a 4-byte Adler-32. It is neither raw DEFLATE nor gzip.

The sender MUST write the real input length, but the receiver treats it as a capacity. After a good decode the receiver uses the bytes it actually got and MUST NOT reject a body for being shorter. Bytes after the zlib stream are ignored. If the zlib data is malformed, Fossil keeps the original bytes and the sync path parses them as cards anyway. Ordinary compression uses zlib's default level, an inline body login uses level 9, and receivers MUST handle any level. Stored blobs use the same container and are retransmitted byte for byte.

§4.2A round is one POST

A round is one POST and its reply, and it ends when the reply body runs out. There is no done or end card, and running out is not an error.

§4.3Two kinds of cookie

The cookie TEXT card travels inside the decoded body. HTTP cookie login (§6.5) is a different mechanism.

§5Cards

§5.1Lines and counted payloads

A body is a sequence of LF-terminated lines. Some cards announce a byte count, and that many bytes follow straight after the card's LF. The payload can contain LF, and it ends only at the count. A cfile sender adds one more LF only when the compressed payload does not already end in one, and receivers read that pad as an empty line. A config payload is always followed by one LF (§9.3).

§5.2Card syntax

A canonical card has tokens separated by one space, no leading or trailing whitespace, and one LF. Operators are lowercase ASCII letters, except clone_seqno. Fossilized arguments MUST be decoded. Senders MUST emit the canonical form. Receivers MUST accept it, and MAY also split on runs of space, tab, VT, FF or CR. There is no maximum line length (§5.2, §11.3).

What happens to a bad card depends on which side reads it and how far it gets:

CaseServer reading a requestClient reading a reply
Unknown operator, wrong arity, or a card sent in the wrong directionDiscards the reply built so far, emits error bad command: LINE, and goes on with later cards. Earlier changes are not rolled back.Logs a local warning, sends nothing, and stops reading this reply. The cards before it still count, and §3.7 is evaluated.
A file, cfile or uvfile handler rejects its cardDiscards the reply so far, emits the handler's error, counts it, and stops reading the request.Logs a warning, keeps the processed prefix, and continues as usual (§10.1).
Extra tokensIgnored beyond the six-token vector. private ignores any arguments. igot HASH X is private only when X is exactly 1, and public otherwise.

No “unknown message” reply text exists (§5.2, Appendix C).

§5.2.1The nineteen operators

login push pull cookie clone file cfile uvfile private igot uvigot gimme uvgimme reqconfig config clone_seqno pragma error message

§5.3Comment lines

A line starting with # is never dispatched as a card. Servers skip it. Clients skip it too, except for the timestamp line that ends a reply:

# timestamp 2026-07-02T18:31:13 errors 0

The timestamp is exactly 19 bytes of UTC, used to estimate clock skew. The error count has no leading zeros and is informational. Senders MUST use this form. Every request ends with a comment of random bytes, which changes the part of the body the login nonce covers. When a server answers pragma req-clusters, a non-empty run of cluster igot cards MUST sit between # sending-clusters and # end-of-clusters. Receivers ignore both lines.

§6Logging in

§6.1The login card

login USER NONCE SIGNATURE

USER is fossilized. NONCE and SIGNATURE are each 40 lowercase hex digits. A request may carry one login, in the body or in the cookie header. A second is fatal, and the server discards its output and emits an error. The users anonymous and nobody, and SSH connections, need no named login. The first clone round sends none.

§6.2The nonce

NONCE is the SHA-1 of every decompressed body byte after the login line's LF, through the end of the body. With cookie login it covers the whole body and none of the HTTP header.

§6.3The shared secret

shared-secret = SHA1(project-code "/" login-name "/" plaintext-password)

The result is 40 lowercase hex digits, and the login name is exactly USER. The calculation applies once the project code is known. The first clone round sends no login card.

§6.4The signature

SIGNATURE = SHA1(NONCE-hex || shared-secret-hex)

The random comment at the end of each request makes every nonce different. The tool below starts with the values from Appendix A.5.

Compute a login

§6.4How the server checks a login

Before reading any card, the server works out the caller's baseline capabilities from its session, cookie, HTTP Basic or remote-user setup. A successful login can only add capabilities to that baseline. A failed one leaves the baseline alone and ends processing.

  1. nobody and anonymous succeed without a signature, and a configured matching remote user is honoured.
  2. For a named user, the server treats the stored credential bytes as the shared secret and compares SHA1(NONCE || stored) with SIGNATURE, in constant time and case-sensitively.
  3. If that fails and the stored credential is not exactly 40 bytes long, it derives the secret from the stored cleartext, the name and its own project code, and tries again.
  4. Separately, NONCE must equal the SHA-1 of the body tail. A stored credential of exactly 40 bytes never gets the cleartext retry, so deployments that need that retry MUST avoid 40-byte credentials.

Either failure keeps HTTP 200, discards the staged output, emits error login failed and stops reading cards. Fossil keeps no replay cache. A login replay for pull alone is not rejected, while a replayed change can collide with the unique nonce column in the receipt table (§6.4, §11.1).

§6.5Cookie login

Newer servers take the login in an HTTP cookie. The client uses it only when the recorded server version and build time pass this gate:

VERSION >= 22700 AND (DATE > 20250727 OR (DATE == 20250727 AND TIME >= 110500))

Cookie: x-f-l-c=login+USER+NONCE+SIGNATURE

Then the client MUST leave out the body login. Spaces become +, and URL-unsafe bytes of the user name are percent-encoded. If the gate fails or no server-version has arrived yet, the client uses body login. Servers MUST accept body login whatever the gate says. Sending both breaks the one-login rule. Appendix A.3 shows the switch: round 1 logs in in the body, and round 2, after the server reported 22800 from 2026-03-11, logs in by cookie.

§7Moving content

§7.1file

file HASH SIZE
file HASH DELTASRC SIZE

SIZE bytes follow, uncompressed. The short form carries the whole artifact. The long form carries a Fossil delta against DELTASRC. Nothing follows the payload. Push and pull use file.

§7.2cfile

cfile HASH USIZE CSIZE
cfile HASH DELTASRC USIZE CSIZE

CSIZE frames the payload, which is the repository's stored compressed artifact or delta, sent byte for byte. USIZE is the full artifact's size, even in the delta form. It is parsed but not checked by the transfer layer. Clone version 3 always uses cfile, with no size threshold, pragma or capability negotiation.

§7.3uvfile and the unversioned cards

uvfile NAME MTIME HASH SIZE FLAGS
uvigot NAME MTIME HASH SIZE          server to client
uvgimme NAME                         client to server

NAME is fossilized and MTIME is a non-negative Unix second. HASH is the content hash, or - for a deletion. Flag 0x0001 marks deletion and 0x0004 means the content is omitted. Senders MUST clear the other bits, and receivers ignore them, so 6 reads as 4. The canonical deletion is HASH -, SIZE 0, flag 1.

Before applying a received uvfile, the receiver MUST recompute its status from the current local row using §8.5.1 and MUST NOT reuse a status it computed for an earlier uvigot. Sending unversioned changes to a server needs UV Write. When a server gets uvgimme NAME it looks the name up and sends nothing if it is absent, or the SHA3 version error for a SHA3 hash and an old client. If its reply has reached the output cap it sends uvigot instead, which brings another request. Otherwise it sends the full uvfile.

§7.4Deltas whose source is missing

A missing DELTASRC does not cause rejection. The receiver keeps the delta under HASH, deletes HASH's phantom and creates a phantom for DELTASRC, private or public to match the content card. HASH is recorded as dangling and is rebuilt later, once its source is available. The draft is explicit that nothing guarantees a later check of HASH against the rebuilt bytes. Fossil handles the source before it can notice that HASH is already stored, so a source phantom can be left behind even when HASH turns out to be a duplicate.

§7.5Private content

A bare private card marks the next file or cfile as private. Other cards and comments do not use up the mark. In a reply it always sets the mark. In a request it sets the mark only if the sender has the Private capability. Otherwise the server emits its authorization error and the content card that follows is treated as public. A client's mark lasts until used or the session ends, and a server's lasts until the end of its request.

  • A sender MUST NOT send a delta against a private source to a peer without Private permission. It sends full content instead.
  • A missing source for a marked delta becomes a private phantom, and for an unmarked delta a public one.
  • igot HASH 1 from a peer without permission is not an error. It creates no phantom but marks an existing HASH private.
  • Pulling private content needs a successful pragma send-private.

§7.6The SHA3 gate

Never send a file or cfile named by a SHA3-256 hash, or a uvfile with a 64-digit hash, to a peer whose recorded VERSION is below 20000. The server treats an unknown client as version 0 until client-version arrives. The client assumes the server runs its own version until it sees server-version. At each refused artifact the sender emits

error Fossil\sversion\s2.0\sor\slater\srequired.

and carries on with the other cards. It never substitutes a SHA1 name. Outside the first clone reply, a server error ends the client's card loop for that reply and §3.7 is evaluated. In the first clone reply, the error is ignored and the client makes its second clone request. When a sync runs automatically after a commit, an error matching %not authorized to write% marks autopush as failed and parsing continues.

§7.7Hash policy on arrival

The hash policy checks the received HASH, not its DELTASRC. Under shun-sha1, a non-clone file with a SHA1 name is read and thrown away, with no error and no change to the repository. A cfile with a SHA1 name is thrown away even during clone, though it still counts as a received card for §3.7(e). The draft points out one dead end. A delta can arrive against a SHA1 source, the client asks for the source, the source is discarded, and the session ends with that phantom unresolved.

Integrity is checked on the rebuilt artifact bytes, not on the wire payload. A repository's commit hook MUST rehash each newly stored artifact whose full bytes are available and abort the commit on a mismatch. Storing and verifying a SHA3-256 artifact under the auto policy permanently moves the repository to sha3.

§8Clone

A clone begins with pragma client-version, clone 3 1 and the random comment, with pragma send-private first when a private sync is requested. The first request carries no login. Later ones use normal authentication.

§8.1Clone version

clone VERSION SEQNO

In version 3, the profile the draft specifies, the server sends cfile cards in storage order with the type application/x-fossil-uncompressed. Fossil accepts higher versions with the same behaviour, but only 3 is specified. A SEQNO of zero or less gets error invalid clone sequence number, a rollback and nothing else, so clients MUST send a positive decimal SEQNO.

§8.2The sequence cursor

SEQNO is a RID, a row number in the server's blob table. The server serves rows from that RID upward and skips missing numbers silently, so clients MUST NOT guess a count or size from the range. An accepting reply carries cfile cards in RID order, with any per-artifact SHA3 errors in place, then clone_seqno NEXT, then push SERVERCODE PROJECTCODE and the closing comment.

The client reissues clone 3 NEXT only if §3.7 says to continue, the reply had a well-formed push, and NEXT is positive. NEXT zero means the server has nothing more, and it bars any further clone, pull or push cards in the session. If §3.7 still wants a round, the client sends a cleanup request with no operation card: login if needed, client-version, pragmas, leftover reqconfig, gimme or uvgimme, the cookie and the random comment. With no direction in force, a gimme in cleanup MUST produce neither content nor error, so any phantom left at that point stays unresolved.

SEQNO := 1
first request := [send-private]; client-version; clone 3 1; randomness
loop:
  send; process reply in order; remember whether a well-formed push came
  if first clone round and error: record any later push, ignore the error,
     keep parsing; the second clone round is mandatory
  if clone_seqno NEXT is decimal: SEQNO := NEXT
  evaluate §3.7
  if continue and push seen and SEQNO > 0: next request has clone 3 SEQNO
  else if continue: next request is the operation-less cleanup
  else stop

Clone rounds have no push direction, so a server ignores any igot a cloning client sends, and a client SHOULD NOT send them. A server MUST accept and ignore igot cards that arrive without push.

§8.3The first clone round

The first request has no login. Any error in its reply is ignored as an error, whether it is about private access, Clone permission or the SHA3 gate. The client reads the rest of the reply, records any push, keeps its unversioned send table as it is, and sends the mandatory second request. Appendix A.2 shows this with a client too old for SHA3 artifacts.

§8.4Configuration during clone

The client holds back reqconfig and uv-hash until after round 0. Once Clone permission is confirmed, a server with unversioned sync enabled sends pragma uv-pull-only and its full unversioned catalog straight away in the clone reply, without waiting for the client's hash.

§8.5Push, pull and sync

push SERVERCODE PROJECTCODE, pull …, or both choose the direction. A projectcode mismatch is fatal. Pulling turns the server's igot cards into client phantoms. Pushing turns the client's igot cards into server phantoms. gimme fetches the content.

§8.5.1Unversioned files

At the start of a session the client fills its send table with every local unversioned row that has a hash and is not marked mtime-only. Tombstones are left out. On the first eligible round, never clone round 0, it sends pragma uv-hash HASH once. HASH is the SHA-1 of one line per non-tombstone row, sorted bytewise by name:

NAME SP YYYY-MM-DD SP HH:MM:SS SP HASH LF

If the hashes match, the server sends no catalog. Otherwise, given Read permission, it sends pragma uv-push-ok or uv-pull-only and then one uvigot for every entry, tombstones included. For each uvigot the client compares the remote entry with its own row and picks one of six outcomes:

StatusWhenWhat the client does
0No local rowAsks for the file with uvgimme, unless the remote entry is a deletion
1Hashes differ and the remote is newerThe remote wins: asks for the content, or records the deletion
2Same hash, remote newerUpdates the local mtime only
3Same hash, same mtimeNothing
4Same hash, local newerSends its mtime, if uploads are allowed
5Hashes differ and the local copy is newerThe local copy wins: sends it, if uploads are allowed

When the times are equal and the hashes differ, the bytewise order of the hashes breaks the tie. Revert maps 4 to 2 and 5 to 1, and dry-run changes nothing. Statuses 0 to 3 remove the name from the send table. A pull-only session removes 4 and 5 too. Each qualifying uvigot appends one uvgimme, with no retry table. When remote content wins, the old local row is deleted at once and is not restored if the transfer later fails. During the upload phase the client sends each selected row from its send table and removes it. If the request grows past the usual output threshold, it stops there and §3.7(b) carries the rest into the next round.

Fossil can send a short, malformed uvigot during upload, and the server treats it as a bad command. The draft calls this a source defect, and a cleanroom sender MUST NOT emit it.

§8.6igot and gimme

igot HASH announces a public artifact, igot HASH 1 a private one, and gimme HASH asks for content. They can come in any order. Peers dated before 2020-04-13 get no private igot at all. The client holds its private inventory back until server-version tells it the peer's date, then appends it to the next request, and §3.7(c) sends that request.

§8.6.1Branches, tags and leaves are derived

No card carries a branch, tag, leaf or closed marker. Each peer derives them from stored artifacts per the Artifact Format and Repository State drafts. The current trunk also depends on each peer's own main-branch setting, so two synced peers can disagree about it. While phantoms remain, the views cover only what is present and can change later without any sync error.

§8.7Phantom records

§3.3 is authoritative.

§8.8Which phantoms to ask for

Each round filters gimme candidates by peer-lacks, shun and private as §3.3 says. The filters belong to the round and are never saved.

§8.9Loop termination

§3.7 is authoritative. The server keeps no state and signals no completion.

§9Pragmas

pragma NAME [ARGUMENTS] is an ordinary card. Unknown names MUST be ignored silently. A known name sent in the wrong direction is treated the same way and MUST NOT change state. A bare pragma with no name is an unknown card and gets error bad command. A known pragma whose condition fails does nothing and raises no error.

§9.1Version negotiation

A full pragma client-version VERSION DATE TIME sets the server's view of the client, with DATE and TIME as YYYYMMDD and HHMMSS, and makes the server answer with a full server-version. A short form with three or four tokens updates only VERSION and gets no answer. The client applies the same rule to server-version. Until one arrives it assumes the peer runs its own release, dated 00000000 000000. In Appendix A.1, 22800 is Fossil 2.28.00.

§9.2Unversioned-file pragmas

The client sends uv-hash at most once, and never in clone round 0. A matching hash gets no response. On a mismatch, a server with Read sends exactly one uv-push-ok if the caller may write unversioned files, or one uv-pull-only otherwise, and then the full catalog. uv-pull-only drops the client's local-only status 4 and 5 entries. The canonical hash is SHA-1, but the server also accepts an artifact hash such as SHA3-256 and treats a mismatch as usual.

§9.3Configuration

reqconfig /NAME asks for a configuration group. Without Read the server ignores it, and an unknown group gets no cards and no error. Clone holds these requests back. The answer is config GROUPNAME SIZE, exactly SIZE bytes, and one mandatory LF. A Fossil-compatible receiver consumes that byte without checking it. Scalar settings always arrive as config /config SIZE with this payload:

MTIME SP 'name' SP value SP 'value'

Values are wrapped in ' with inner quotes doubled. Table groups use their own group name, and their row format is out of scope. A server MUST require Admin to apply a pushed config card, and otherwise emits error not authorized to push configuration. A config card whose SIZE is not plain decimal takes the unknown-card path. The four transfer-hook settings travel as scalar /config and run only on the server.

§9.4Check-in locks

pragma ci-lock HASH CLIENT-ID asks for a check-in lock on HASH, kept as a ci-lock-HASH row on the server. The server first deletes lock rows that have timed out or whose HASH is no longer a leaf. If a live lock on HASH remains and it belongs to a different client, the server replies pragma ci-lock-fail LOGIN MTIME. If it belongs to the same client, the server says nothing. Otherwise it writes a new lock and sends no acknowledgement. Silence after ci-lock confirms nothing. pragma ci-unlock CLIENT-ID deletes that client's locks and any invalid rows, again with no reply and no Write check. The client sends it whenever it has a stored ID and no current lock, so it may repeat.

§9.5Private content and discovery

  • send-private turns on private sync only for a caller with x. Otherwise it appends error not authorized to sync private content without discarding the reply. Clients repeat it in every private round.
  • send-catalog makes a read-authorized server announce every eligible artifact it holds, after the §3.3 filters.
  • req-clusters asks for public cluster igot cards, wrapped in the §5.3 comments.
  • req-links lets the reply to that request carry pragma link URL ARG MTIME. Without it the server MUST send no links. The client stores ARG verbatim and MUST NOT parse, change or forward it. Links are optional, and they say nothing about artifacts.
  • client-url URL is stored by a server whose caller has Write, as syncfrom: followed by a normalised URL, unless the host contains localhost. The draft spells the normalisation out in detail.
  • avoid-delta-manifests makes the client send full manifests, not deltas, for the rest of the session.

§10Errors and messages

§10.1The error card

error TEXT

TEXT is fossilized and MUST be decoded. HTTP status stays 200 throughout. On the server, each request that reaches card processing runs in one database write transaction, and errors fall into three kinds:

KindExamplesServer outputTransaction
AppendSHA3 gate, unauthorized send-privateError added, parsing continuesCommits at the end of the request
ResetWrong project, authorization, duplicate login, unknown cardPartial output discarded, then the errorEarlier changes still commit
Fail-fastinvalid clone sequence number, invalid config recordError and stopRolled back

A failure before card processing, such as a schema-out-of-date response, returns before any transaction opens. A refused clone is a reset site that still writes push before the error.

On the client, an ordinary server error commits the cards already processed, ends that reply's card loop and sends the client to §3.7. It ends the session only if §3.7 finds nothing to do. Errors in the first clone reply are dropped as errors while the rest of the reply is still read. A content or integrity error found by a handler gives a warning and processing continues as usual. Only an explicit fail-fast path rolls back the round and stops. A private mark already used up by a handler is not restored by a rollback.

§10.2The message card

message TEXT

A message has exactly two tokens, is decoded and is never fatal. A client MAY show it and MUST change no state, with one exception. If push is on and the text matches the glob pull only *, case-sensitively, the client turns push off for the session and hides the message. Cards already queued for the next request stay queued, but later gimme cards in the same reply MUST NOT append content. Later requests carry no push, while unversioned uploads stay allowed.

§11Security considerations

  • Body login sends a user, a nonce and a signature, never the password. HTTP Basic and proxy credentials are outside that property.
  • A sender MUST enforce the 20000 SHA3 gate and MUST NOT truncate, rename or downgrade SHA3 names (§11.4).
  • There is no login replay cache. A byte-for-byte replay with a valid signature is not rejected for that reason. The nonce stored with a change's receipt is unique, but that is a separate matter from replay protection (§11.1).
  • Nothing stops sync over plain HTTP, which exposes logins, private artifacts and cookie logins to anyone reading the traffic. Deployments SHOULD use HTTPS, SSH or another confidential, integrity-protected, server-authenticated transport (§11.2).
  • There is no per-line limit. Payload sizes come from declared counts and storage policy (§11.3).

App. AExamples

The examples show decompressed bodies. The replay tool in §3 steps through A.1, A.2 and the last scenario of A.3.

A.1Push and pull in two rounds

The client announces three artifacts. The server asks for two and announces two of its own, so the client makes two phantoms. In round 2 each side sends the other what it asked for, and no round 3 is needed. Anonymous push and pull are allowed, so no login appears. The first file payload in round 2 is a 272-byte manifest of seven lines, each ending in LF, and the second is the 26-byte line alpha content from client with its LF. The reply's payloads are exactly 270 and 31 bytes. The counts frame them, and the lines inside are payload, not cards.

A.2The SHA3 gate in a clone

A client reporting release 19999 asks to clone. The server refuses a SHA3 artifact with the version error, then sends clone_seqno 0 and a push. No SHA1 fallback happens, and the client still makes the required second request.

A.3Private content

An anonymous pull never sees private artifacts. A crafted gimme for a private hash gets an igot … 1 announcement. An unauthorized send-private gets an error and the public inventory. An authorized user logs in, pulls, and receives two private files, the second as a delta against a public artifact.

A.4Comment lines

Random comments are ignored as cards. The timestamp estimates clock skew, and errors 0 is informational.

A.5Authentication

The user, password, project code and covered body behind the three SHA-1 values loaded into the §6 tool.
